## 第 0 课 · 概念 + 环境(先读后敲)

**核心认知(背下来)**:

- **工作流(workflow)= 人写死流程**;**Agent = 模型自己决定路径**。Anthropic 原文的分界线就这一句:预定义代码路径的是工作流,模型临场决定步骤的才是 Agent
- 五种模式,按复杂度递增:**prompt chaining(链)→ routing(路由)→ parallelization(并行)→ orchestrator-workers(编排)→ evaluator-optimizer(评审循环)**
- 单 Agent 的三个天花板:上下文越堆越杂、工具多了选择就乱、任务只能串行。多 Agent/工作流是解药——**但每一副药都有成本**:多一次 LLM 调用 = 多一份钱、多一段延迟、多一个失败点
- 最重要的判断(倒背如流):**能用一个 prompt 解决的不拆;拆固定步骤的不并行;能单 Agent 的不上多 Agent**

## 第 1 课 · llm_client.py + prompt chaining(链式流水线)

**目标**:搭好带账本的 `llm_client`,然后写最简单的组合模式——**链**:固定步骤依次执行,上一步输出是下一步输入。

**新概念**:
- 链 = 流水线,**没有分支、没有判断**——所以它是"工作流"而不是 Agent
- 每一步**单一职责 + 各自的 system prompt**,中间结果可检查:跑偏了好定位是哪一环(比一个巨型 prompt 强)
- 阶段 3 的 RAG(切块→向量化→检索→塞 prompt)其实就是一条链——你早就写过了
- `usage` 对象:每次响应都带 token 数,账本靠它记账

**`llm_client.py`**:

```python
"""所有 LLM 调用的唯一出口,自带成本账本。单价是示例,按你平台价目表改"""
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()

client = OpenAI(
    api_key=os.environ.get("OPENAI_API_KEY"),
    base_url=os.environ.get("OPENAI_BASE_URL"),
)
CHAT_MODEL = os.environ.get("MODEL_NAME")

PRICE_IN, PRICE_OUT = 2.0, 8.0        # 示例单价(元/百万 token)
BILL = {"calls": 0, "in": 0, "out": 0, "cost": 0.0}


def chat(messages, **kwargs):
    """记账版聊天:返回 (回复文本, usage)"""
    resp = client.chat.completions.create(model=CHAT_MODEL, messages=messages, **kwargs)
    u = resp.usage
    BILL["calls"] += 1
    BILL["in"] += u.prompt_tokens
    BILL["out"] += u.completion_tokens
    BILL["cost"] += u.prompt_tokens / 1e6 * PRICE_IN + u.completion_tokens / 1e6 * PRICE_OUT
    return resp.choices[0].message.content, u


def bill():
    return (f"账单:调用 {BILL['calls']} 次 | 输入 {BILL['in']} tok | "
            f"输出 {BILL['out']} tok | 约 ¥{BILL['cost']:.4f}")
```

**`01_chain.py`** —— 周报生成器,三步链:

## 第 2 课 · 02_router.py — routing(路由分发)

**目标**:一次轻量分类调用,把问题分发给不同的"专家"(各自的 system prompt)。这是你阶段 3"意图识别没做好"的正式解法之一。

**新概念**:
- 路由 = **轻量决策**(分类小调用)+ **专家执行**(重提示)。决策要快、要便宜、要可兜底
- 分类用 **Pydantic 收紧取值**(category 枚举)+ `other` 兜底类——分类永远会错,错要错得安全
- 和 function calling 的分工:**function calling 让模型在工具间挑**;router 是**你写死的分支**——更可控、可单测、可限流。两者的选择标准:分支逻辑要不要模型"理解"内容
- Java 视角:这就是网关路由 + 策略模式

**`02_router.py`**:

```python
from pydantic import BaseModel, Field, ValidationError

import llm_client


class Route(BaseModel):
    category: str = Field(description="必须取值:leave(考勤假期)/it(IT问题)/dev(研发规范)/other(其他)")
    reason: str = Field(description="一句话判断依据")


ROUTES = {
    "leave": "你是考勤假期专员,精通公司年假病假调休制度,只回答考勤假期问题,简洁。",
    "it": "你是 IT 支持专员,精通公司 VPN/账号/设备流程,只回答 IT 问题,简洁。",
    "dev": "你是研发规范专员,精通公司分支/评审/发布/值班规范,只回答研发规范问题,简洁。",
    "other": "你是通用助手。这个问题不在你的专长范围,诚实说明不确定,禁止编造。",
}


def route(question):
    """轻量分类:一次小调用 + 校验失败兜底"""
    raw, _ = llm_client.chat(
        [
            {"role": "system", "content":
                "你是问题分类器。只输出一个 JSON 对象,字段定义:\n"
                f"{Route.model_json_schema()}"},
            {"role": "user", "content": question},
        ],
        response_format={"type": "json_object"},
    )
    try:
        return Route.model_validate_json(raw)
    except ValidationError:
        return Route(category="other", reason="分类失败,走兜底")


def answer(question):
    r = route(question)
    print(f"(路由 → {r.category} | {r.reason})")
    reply, _ = llm_client.chat([
        {"role": "system", "content": ROUTES[r.category]},
        {"role": "user", "content": question},
    ])
    return reply


if __name__ == "__main__":
    for q in ["年假最多能攒几天?", "VPN 连不上怎么办?",
              "MR 超过 3 天没处理会怎样?", "今天天气怎么样?"]:
        print(f"\n你:{q}")
        print(f"AI:{answer(q)}")
    print("\n" + llm_client.bill())
```

**自测/实验**:
1. "我年假没休完能折算成钱吗?"——在 leave 和 other 的边界上,看分类器怎么判,错了吗?
2. 分类器调用能不能换更便宜的小模型?(决策和执行分离的最大红利)
3. 想一想:`route()` 要写单测的话,mock 掉什么就够?

## 第 3 课 · 03_parallel.py — parallelization(并行评审)

**目标**:三个评审员**同时**评一份草稿。并行用标准库 `ThreadPoolExecutor`——Java 视角就是 `ExecutorService`,你闭着眼都会。

**新概念**:
- 并行的收益 = 总延迟从"之和"变"之和的最大值"(I/O 密集型任务都适用,LLM 调用是典型)
- `pool.submit(fn, *args)` 排队即跑返回 Future;`future.result()` 收割——**worker 里的异常在这一刻才抛出**(submit 时不会报)!
- `max_workers` 控并发数:LLM 平台有速率限制,不是越大越好
- 线程里调 LLM 没问题(I/O 等待);但**别在线程里碰同一个事件循环的异步资源**——阶段 5 的 `MCPToolbox._await` 用了 `run_coroutine_threadsafe`,它恰好是线程安全的,多线程共享一个 toolbox 可以直接用
- 什么时候并行:各路任务**互不依赖**。有依赖就只能链(第 1 课)

**`03_parallel.py`**:

```python
import time
from concurrent.futures import ThreadPoolExecutor

import llm_client

DRAFT = "星链公司新规定:年假可以随时休,不需要审批,休完为止。"

REVIEWERS = [
    ("事实核查", "你是事实核查员。对照公司真实制度(年假 10 天起、需 OA 审批),只列出草稿与制度不符之处。"),
    ("合规审查", "你是合规专员。指出这段话可能误导员工的地方(比如让人以为不用审批),只列问题。"),
    ("文字评审", "你是文案评审。指出这段话的表达问题(歧义、缺上下文、太武断),只列问题。"),
]


def review(name, prompt):
    t0 = time.time()
    reply, _ = llm_client.chat([
        {"role": "system", "content": prompt},
        {"role": "user", "content": f"评审这段文字:\n{DRAFT}"},
    ])
    return name, reply, time.time() - t0


if __name__ == "__main__":
    t0 = time.time()
    with ThreadPoolExecutor(max_workers=3) as pool:
        futures = [pool.submit(review, n, p) for n, p in REVIEWERS]
        results = [f.result() for f in futures]     # ★ worker 的异常在这一刻抛出
    for name, reply, seconds in results:
        print(f"=== {name}({seconds:.1f}s)==\n{reply}\n")
    print(f"并行总耗时 {time.time() - t0:.1f}s")
    print(llm_client.bill())
```

**自测/实验**:
1. `max_workers=1` 再跑一遍——耗时变成三倍,这就是"假并行"
2. 把某个评审员的 prompt 改成会让模型抛异常的(比如传非字符串),确认异常在 `f.result()` 处浮出——然后在 `review` 里加 try/except 兜底成"(该路评审失败)",体会"单路失败不炸全局"
3. 心算:如果 10 个评审员、每人 5 秒,串行 vs 并行(max_workers=10)各多久?

## 第 4 课 · 04_orchestrator.py — orchestrator-workers(主管-工人)

**目标**:复杂任务的第一种正解——**主管拆任务,工人并行干,汇总收尾**。和链的本质区别:**拆成几个子任务由模型临场决定**。

**新概念**:
- 三个角色:**plan**(主管拆解,Pydantic 校验任务列表)→ **workers**(并行执行,互不依赖)→ **synthesize**(汇总合成)
- 主管的输出是**任务描述,不是答案**——职责分离,每层 prompt 都短
- `pool.map(worker, subs)`:按提交顺序返回结果、异常直接抛——比 submit+result 少两行
- 风险预告:worker 的材料拼进汇总 prompt,**材料太长会撑爆上下文**——截断或分批汇总(生产上的 map-reduce)

**`04_orchestrator.py`**:

```python
from concurrent.futures import ThreadPoolExecutor

from pydantic import BaseModel, Field

import llm_client


class Subtasks(BaseModel):
    subtasks: list[str] = Field(description="3 到 4 个可独立回答、彼此不重叠的子问题")


def plan(topic):
    """主管:拆任务。输出是任务清单,不是答案"""
    raw, _ = llm_client.chat(
        [
            {"role": "system", "content":
                "你是调研主管。把主题拆成 3-4 个可独立回答的子问题。"
                "只输出 JSON:{\"subtasks\": [\"...\"]}"},
            {"role": "user", "content": topic},
        ],
        response_format={"type": "json_object"},
    )
    return Subtasks.model_validate_json(raw).subtasks


def worker(sub):
    """工人:独立回答一个子问题"""
    reply, _ = llm_client.chat([
        {"role": "system", "content": "你是调研员。简洁回答子问题,分点,150 字内,不知道就说不确定。"},
        {"role": "user", "content": sub},
    ])
    return sub, reply


def synthesize(topic, pairs):
    """汇总:合成报告"""
    material = "\n\n".join(f"【{s}】\n{r}" for s, r in pairs)
    reply, _ = llm_client.chat([
        {"role": "system", "content":
            "你是报告撰写员。综合全部调研材料写短报告:第一句给结论,分节陈述,结尾列遗留问题。"},
        {"role": "user", "content": f"主题:{topic}\n\n{material}"},
    ])
    return reply


if __name__ == "__main__":
    topic = "公司要不要引入 AI 客服?"
    subs = plan(topic)
    print(f"主管拆出 {len(subs)} 个子任务:", *subs, sep="\n  - ")

    with ThreadPoolExecutor(max_workers=4) as pool:
        pairs = list(pool.map(worker, subs))

    print("\n=== 最终报告 ===")
    print(synthesize(topic, pairs))
    print("\n" + llm_client.bill())
```

**自测/实验**:
1. 把主题换成"公司班车制度的改进空间",看主管这次拆出了什么——**同一个主管,不同主题,拆法不同**:这就是它和链的区别
2. 给 `worker` 加 try/except,失败返回"(该子任务失败)"——毕业考要求这个兜底,先练
3. 假想子任务有 20 个:汇总 prompt 会多长?想一个截断策略

## 第 5 课 · 05_evaluator.py — evaluator-optimizer(评审循环)

**目标**:生成 → 评审 → 按意见改 → 再评审……直到通过或到达轮数上限。质量门槛模式,也是最容易**失控**的模式。

**新概念**:
- 评审员必须**苛刻 + 有明确 rubric**——标准越具体,越不会"感觉还行"地摸鱼
- 评审输出的 issues 要**可执行**:生成端能照着改(要改什么、改成什么)
- **MAX_ROUNDS 是安全带**:现实中存在永不满意的评审(rubric 自相矛盾、评审员风格偏执),循环必须有终点
- 和 Agent 循环的区别:这里**轮次内容由评审意见驱动**,不是模型自由发挥

**`05_evaluator.py`**:

```python
from pydantic import BaseModel, Field, ValidationError

import llm_client


class Verdict(BaseModel):
    passing: bool = Field(description="是否通过全部评审标准")
    issues: list[str] = Field(description="不通过时逐条列出问题;通过时为空数组")


RUBRIC = ("评审标准:1)有明确的起止日期;2)说明了替代充电方案;"
          "3)留了联系人;4)全文不超过 100 字。")


def generate(feedback=None):
    """生成端:没有初稿就写初稿,有评审意见就按意见改"""
    if feedback is None:
        messages = [
            {"role": "system", "content": "你是公司行政,负责写全员公告。"},
            {"role": "user", "content": "写一条充电桩停用维护的公告,面向全员。"},
        ]
    else:
        messages = [
            {"role": "system", "content": "你是公司行政,负责写全员公告。"},
            {"role": "user", "content": "写一条充电桩停用维护的公告,面向全员。"},
            {"role": "assistant", "content": feedback["draft"]},
            {"role": "user", "content": f"评审意见:\n{feedback['issues']}\n按意见修改,只输出修改后的公告。"},
        ]
    text, _ = llm_client.chat(messages)
    return text


def evaluate(text):
    raw, _ = llm_client.chat(
        [
            {"role": "system", "content":
                f"你是苛刻的评审员。{RUBRIC}\n只输出 JSON,字段定义:\n"
                f"{Verdict.model_json_schema()}"},
            {"role": "user", "content": text},
        ],
        response_format={"type": "json_object"},
    )
    try:
        return Verdict.model_validate_json(raw)
    except ValidationError:
        return Verdict(passing=False, issues=["评审输出不合格,按原意见继续改"])


MAX_ROUNDS = 3
draft, feedback = None, None
for round_i in range(1, MAX_ROUNDS + 1):
    draft = generate(feedback)
    v = evaluate(draft)
    print(f"--- 第 {round_i} 轮 ---\n{draft}\n评审:{'✅ 通过' if v.passing else v.issues}\n")
    if v.passing:
        break
    feedback = {"draft": draft, "issues": "; ".join(v.issues)}
else:
    print("(达到最大轮数,带病发布——遗留问题要记录在案!)")

print(llm_client.bill())
```

**自测/实验**:
1. 初稿第一轮**必然**不通过(没写日期)——确认循环真的转起来了
2. 给 RUBRIC 加一条自相矛盾的标准("不超过 100 字"vs"不少于 200 字"),看它耗尽 MAX_ROUNDS——这就是安全带存在的理由
3. 把 issues 改得含糊("写得更好点"),对比修改效果——**可执行的意见才有用**

## 第 6 课 · 06_cost.py — 成本与延迟账本(动手量一量)

**目标**:给"要不要编排"一个量化决策方法。每一笔编排开销都要能回答:**多花的钱和时间,买到了什么?**

**新概念**:
- 决策树(从便宜往贵走):单 prompt → 链 → 路由 → 并行 → 编排 → 评审循环。**能停在左边就别去右边**
- 成本模型:一次编排的 token ≈ 各层之和;主管拆得越碎,worker 越多,汇总材料越长——**成本是乘法不是加法**
- 延迟模型:串行链 = 各步之和;并行 = 最大一路;评审循环 = 轮数 × (生成+评审)
- 有了账本,这些不再是感觉:`llm_client.BILL` 已经在帮你记

**`06_cost.py`**(把第 4 课和"单 prompt 直接问"放上天平):

```python
import llm_client
from orchestrator import plan, worker, synthesize   # 第 4 课的三个函数
from concurrent.futures import ThreadPoolExecutor

TOPIC = "公司要不要引入 AI 客服?"

# 方案 A:单 prompt 直接问
a, _ = llm_client.chat([
    {"role": "system", "content": "你是调研顾问。就这个主题写一份短报告:结论先行,分点陈述。"},
    {"role": "user", "content": TOPIC},
])
print(f"=== 方案 A(单 prompt)==\n{a}\n")

# 方案 B:编排(重新计账:先抄下当前账单,再算差值)
before = dict(llm_client.BILL)
subs = plan(TOPIC)
with ThreadPoolExecutor(max_workers=4) as pool:
    pairs = list(pool.map(worker, subs))
b = synthesize(TOPIC, pairs)
print(f"=== 方案 B(编排)==\n{b}\n")

after = llm_client.BILL
used_in = after["in"] - before["in"]
used_out = after["out"] - before["out"]
print(f"方案 B 额外花销:{after['calls'] - before['calls']} 次调用,"
      f"{used_in + used_out} tokens —— 是方案 A 的几倍?报告质量好多少?")
print(llm_client.bill())
```

**自测/实验**:
1. 算一算:方案 B 的 token 是 A 的几倍?报告真的好那么多吗?——**这就是"什么时候坚决不用多 Agent"的判断练习**
2. 把账本单价改到你平台的真实价格,算这个月如果每天跑 100 次要多少钱
3. 把延迟也算上:方案 A 一次调用 ~3s;方案 B 串了三层+并行——各多少秒?(在 chat 里记时间)

## 常见报错速查

| 报错/现象 | 原因 | 解决 |
|---|---|---|
| worker 明明炸了,submit 时没报 | 异常在 `future.result()` 收割时才抛 | 在 worker 内部 try/except 兜底成文本;result 处也要防 |
| `ValidationError`(拆解/路由/评审) | 模型输出不合 Schema | response_format + 重试;枚举值写进 Field description |
| 汇总时 400 / 回答被截断 | worker 材料拼太长,撑爆上下文 | 材料超长截断;或分批汇总再汇总(map-reduce) |
| 评审永不通过 | rubric 自相矛盾 / 意见不可执行 | MAX_ROUNDS 兜底;每条意见必须"可照着改" |
| 多线程里调 LLM 偶发连接错误 | 平台速率限制 | max_workers 调小;捕获后重试一次 |
| 账单金额看着不对 | PRICE_IN/PRICE_OUT 是示例价 | 按你平台价目表换真实单价 |
| 各 worker 结果顺序乱掉 | 用了 submit + as_completed | 要顺序用 `pool.map`;要"先到先得"用 `as_completed` |

**卡住的标准动作不变**:读报错最后一行 → 搜索 → 超 30 分钟,代码 + 完整报错 + 你跑的原话一起贴给 ZCode。
