## 一、为什么 MCP 世界全是 async

MCP client 和 server 是两个进程,靠子进程的 stdio 管道说话。client 的一天全是这样:

```
发 initialize 请求 → 等 server 回复
发 list_tools 请求 → 等 server 回复
发 call_tool 请求 → 等 server 回复
```

**全是"发出去,然后等"**——典型的 I/O 密集。你在 Java 后端习惯了"线程池 + 阻塞 I/O":每个等待占住一个线程,线程闲着但占着 1MB 栈。连接少时无所谓;但 stdio_client 的管道、会话、心跳是**常驻**的,再加上"同一时刻挂起 N 个等待"的需求,单线程事件循环是最省的方案。MCP 官方 SDK 选了 asyncio,于是整个生态都是 async。

Java 21 的虚拟线程(Loom)是 Java 版的答案:写法照旧阻塞,底层帮你让出。Python 的答案更进一步:**让出是显式的,就是 `await`**。

## 二、一张表:三套并发模型

| | Java 平台线程 | Java 虚拟线程 | Python asyncio |
|---|---|---|---|
| 调度方式 | OS 抢占式 | JVM 调度,阻塞时自动让出载体线程 | 事件循环,**协作式:`await` 处才让出** |
| 单个成本 | ~1MB 栈 | 几百字节 | KB 级协程对象 |
| 心智模型 | 一件事一个线程 | 写起来和左边一样 | **单线程** + await 切换点 |
| 阻塞调用的代价 | 只卡自己 | 只卡自己 | **卡死整个事件循环**(最大的坑) |
| 心智原型 | Thread/线程池 | Loom | **Netty 的 EventLoop** + 语法级 await |

Java 类比锚点:**事件循环 ≈ Netty 的 EventLoop**(单线程转着队列,遇到 I/O 就注册回调)。区别是 Python 把"回调地狱"用 `await` 语法糖拉直了——比 Reactor 的 Mono/Flux 可读性好得多。

## 三、语法逐条对照(核心,建议打印)

| Python | 意思 | Java 里最接近的写法 |
|---|---|---|
| `async def f():` | 定义**协程函数**。调用它**不执行**,返回一个协程对象 | `Supplier<CompletableFuture<T>>`,拿到的是"待运行的描述" |
| `await coro` | 等协程出结果;**等的时候把线程让给 loop 跑别的** | `future.get()`,但 get 是阻塞占线程,await 是挂起让线程 |
| `asyncio.run(main())` | 建事件循环 → 跑到完 → 关闭。一个进程当主入口用**一次** | 提交总任务并等整个生命周期结束 |
| `asyncio.gather(a, b, c)` | 并发跑多个,全好了才往下走 | `CompletableFuture.allOf(...)` |
| `asyncio.create_task(coro)` | 立刻排队开跑,不等它,拿到 Task 可以后续 await | `executor.submit(task)` |
| `asyncio.sleep(s)` | **挂起,让出线程**,loop 继续跑别的 | `Thread.sleep` 的"理想形态" |
| `time.sleep(s)` | **阻塞整个线程**——loop 在这个线程上,全队陪葬 | 就是 `Thread.sleep`,在 EventLoop 线程上调用是事故 |
| `async with x as y` | 异步版的 try-with-resources,进/出都可能要 await | try-with-resources,但 close() 也是异步的 |
| `asyncio.to_thread(fn)` | 把阻塞函数扔线程池跑,loop 不卡 | `CompletableFuture.supplyAsync(fn, blockingPool)` |
| `loop.call_soon_threadsafe(fn)` | 从别的线程安全地往 loop 队列投一个任务 | `eventLoop.execute(...)`(Netty 就是这么跨线程投递的) |
| `asyncio.run_coroutine_threadsafe(coro, loop)` | 跨线程投协程,返回 concurrent.Future | 把任务投到指定的 EventLoopGroup,再 `.get()` |

两个最容易懵的点,单独说:

**1. `async def` 的函数,直接调用不执行。**

```python
async def fetch(): return 42

x = fetch()        # x 是 coroutine 对象,函数体一行没跑!
print(x)           # <coroutine object fetch at 0x...>
```

Java 类比:`Supplier<CompletableFuture<T>> s = this::fetch;`——你只是拿到了"怎么跑的说明书"。必须有人去启动它:`await x` / `asyncio.run(x)` / `asyncio.create_task(x)`。

**2. `await` 和 `future.get()` 的本质区别。**

```python
result = await session.call_tool(...)   # 线程没闲着,loop 在跑别的协程
```

`get()` 是把当前线程钉死在原地;`await` 是"我在等,线程先还给你,结果好了叫我"。这就是为什么一个线程能同时伺候 N 个会话。

## 四、单线程心智模型:什么会"卡住谁"

- 协程之间是**协作式**多任务:`await` 是**唯一的切换点**
- 两个 `await` 之间的代码**原子执行**,不会被别的协程插进来 → 很多场景不需要锁(Java:你在 EventLoop 里写的 handler 也从不加 synchronized)
- 反过来,**任何不发生 await 的长计算/阻塞调用都会卡死全局**:`time.sleep`、`requests.get`、大 JSON 序列化、死循环——loop 是单线程,它一卡,所有会话、所有心跳全停

自查口诀:**async 函数体里,除了 await,不允许出现任何"等"**。真有阻塞调用,`await asyncio.to_thread(阻塞函数)` 丢进线程池——Java 里你也不会在 Netty 的 EventLoop 里跑 JDBC,一样的道理。

## 五、对着你的代码逐段读(核心章节)

### 5.1 `client.py`:三层 async with

```python
async with stdio_client(SERVER) as (read, write):   # ① 起子进程,拿到管道两端
    async with ClientSession(read, write) as session:  # ② 在管道上建协议会话
        init = await session.initialize()              # ③ 发握手请求,等回复
```

- 每个 `async with` 都持有一个**需要在退出时异步清理**的资源(关管道、关会话)——这就是它存在的意义,`AsyncExitStack` 是把很多个 try-with-resources 叠起来的工具
- 三个 `await` 全是"发协议消息 → 等对端回复":等待期间这个线程可以(并且确实会)去跑别的协程

### 5.2 `file_server.py`:工具明明是同步函数,为什么能用?

```python
@server.tool()
def read_file(path: str) -> str:   # ← 普通 def,不是 async def!
```

SDK 在调度工具时发现你是同步函数,会自动帮你 `await asyncio.to_thread(read_file, ...)` 扔线程池——**阻塞发生在线程池,不伤 loop**。所以 server 端写普通文件 I/O 函数完全没问题。你以后写 async 工具也行,SDK 两种都接。

### 5.3 `mcp_client.py`:三个世界(本补课的终点)

```
┌─────────────────────┐  run_coroutine_threadsafe   ┌──────────────────────┐
│ 主线程(同步世界)     │ ──────────────────────────→ │ 后台线程(异步世界)     │
│ agent_main.py       │ ← .result() 等结果          │ loop 常驻:            │
│ input() 循环        │                              │  stdio_client × N     │
│ 阶段4的 Agent 循环   │ ──────────────────────────→ │  ClientSession × N    │
└─────────────────────┘      call_soon_threadsafe     └──────────────────────┘
```

**为什么必须有个后台线程跑 loop?** 因为 `ClientSession`、stdio 管道是**绑定在某个 loop 上的常驻资源**,不能每次调用工具都 `asyncio.run` 一遍——那意味着每次都起子进程、握手、然后全部关掉。你的主线程又是同步的 `input()` 循环。解法:开一个线程专门跑 loop,让异步世界常驻;主线程用同步方法跟它打交道。

逐行对应:

| 你的代码 | 在干什么 | Java 对应 |
|---|---|---|
| `self._loop = asyncio.new_event_loop()` | 给后台线程造一个事件循环 | `new NioEventLoopGroup(1)` |
| `threading.Thread(target=self._run, daemon=True)` | 后台线程跑 loop;daemon=主程序退出它就陪葬 | `setDaemon(true)` |
| `asyncio.set_event_loop(self._loop)` | 把 loop 绑定为"这个线程的当前 loop" | 把 EventLoop 绑到线程 |
| `loop.run_until_complete(self._serve())` | loop 跑 `_serve` 直到它结束 | EventLoop 启动 |
| `async with AsyncExitStack() as stack: ... enter_async_context(...)` | 把 N 个 `async with` 叠起来,退出时按反序异步清理 | 把多个资源登记到一个大的 try-with-resources |
| `self._ready = threading.Event()`;`_ready.wait(60)` | 主线程等异步世界就绪 | `CountDownLatch.await(60, SECONDS)` |
| `self._close = asyncio.Event()`;`await self._close.wait()` | 异步世界的"常驻直到被叫停" | `latch.await()` 挂住协程 |
| `asyncio.run_coroutine_threadsafe(coro, self._loop).result(timeout=120)` | **把协程投到后台 loop 执行,当前线程等结果** | 投到指定 EventLoopGroup 后 `future.get(timeout)` |
| `self._loop.call_soon_threadsafe(self._close.set)` | 从主线程安全地通知 loop"该收摊了" | `eventLoop.execute(() -> latch.countDown())` |
| `self._thread.join(10)`;`self._loop.close()` | 等后台线程收完尾,再关 loop | join + 关闭 EventLoopGroup |

一句话总结这个类:**把异步世界关进一个线程,给同步世界开三个同步方法的窗口**(`get_openai_tools` / `call_tool` / `tool_names`)。这就是为什么 `agent_main.py` 里阶段 4 的循环"一个字没改"。

## 六、四大坑(错误示范 + 现象)

**坑 1:忘记 await——什么都没发生**

```python
session.list_tools()          # ❌ 拿到 coroutine 对象,没人跑它
# 现象:RuntimeWarning: coroutine 'ClientSession.list_tools' was never awaited
# Java 类比:submit() 完不 get(),以为做完了,其实任务还在队列里睡觉
```

**坑 2:在 async 函数里用阻塞调用**

```python
async def my_tool(x):
    time.sleep(3)             # ❌ 卡死整个 loop:所有会话、心跳全停 3 秒
    requests.get(...)         # ❌ 同罪
# 解法:await asyncio.to_thread(阻塞函数)
# Java 类比:在 Netty EventLoop 线程里跑 JDBC——你写 Netty 时绝不会这么干
```

**坑 3:在同步函数里写 await**

```python
def main():
    await session.initialize()   # ❌ SyntaxError:await 只能在 async def 里出现
```

同步世界进入异步世界只有一扇门:`asyncio.run(...)`(当主入口)或 `run_coroutine_threadsafe(...)`(往别的线程的 loop 投)。

**坑 4:对常驻资源反复 asyncio.run**

```python
def call_tool(name, args):
    async def one_shot():
        async with stdio_client(SERVER) as (r, w):
            async with ClientSession(r, w) as s:
                await s.initialize()
                return await s.call_tool(name, args)
    return asyncio.run(one_shot())   # ❌ 每次调用:起子进程→握手→调用→全关掉
```

能跑,但每次工具调用都重启整个世界。`MCPToolbox` 的存在就是为了**让会话常驻、只握手一次**。

## 九、速查表(用的时候回来抄)

```python
# ── 入口 ────────────────────────────────────────────
asyncio.run(main())                    # 程序总入口,一次
# ── 并发 ────────────────────────────────────────────
r = await coro                         # 等一个
rs = await asyncio.gather(c1, c2, c3)  # 等一批(Java: allOf)
t = asyncio.create_task(coro)          # 先跑着,回头 await t(Java: submit)
# ── 阻塞逃生门 ──────────────────────────────────────
await asyncio.to_thread(blocking_fn, arg)
# ── 资源 ────────────────────────────────────────────
async with ctx() as c: ...             # 异步 try-with-resources
# ── 跨线程(同步世界 ↔ 异步世界)─────────────────────
fut = asyncio.run_coroutine_threadsafe(coro, loop)   # 投
result = fut.result(timeout=30)                      # 等(Java: get)
loop.call_soon_threadsafe(fn)                        # 安全投个信号
# ── 跨线程标志位 ────────────────────────────────────
ev = threading.Event(); ev.wait(60); ev.set()        # ≈ CountDownLatch
```
